# S8C.0 — Proposed marketplace integration architecture

Research date: **2026-09-24**. This is a reviewable **proposal**, not a frozen ADR or connector implementation. It extends [ADR-0023](architecture/ADR-0023-s8b-commerce-foundation.md) without changing its module ownership: Commerce owns normalized offer/listing/provider state; Pricing remains local pricing authority; Sales owns canonical realized Sale; Product/Catalog remains the technical product master. The [official discovery](S8C0-OFFICIAL-PROVIDER-DISCOVERY.md), [capability matrix](S8C0-CAPABILITY-MATRIX.md), [auth/security](S8C0-PROVIDER-AUTH-AND-SECURITY.md) and [sync/limits](S8C0-SYNC-AND-RATE-LIMITS.md) supply evidence and unresolved gates.

## Future boundaries and ports

Keep the modular monolith. Provider HTTP/signing/DTO translation belongs in provider-specific infrastructure packages, e.g. `Verce.Infrastructure.Marketplaces.MercadoLivre`, `.Shopee`, `.TikTokShop`, or the repository-consistent equivalent chosen at implementation review. No provider field or versioned response type should become a Commerce/Sales aggregate field merely because one API returns it. The package split is useful because ML uses site/resource-specific flows and TikTok uses versioned paths and signed requests [ML-AUTH](https://developers.mercadolivre.com.br/autenticacao-e-autorizacao), [TT-VERSION](https://partner.tiktokshop.com/docv2/page/api-versioning); Shopee package shape waits for official BR docs.

Propose **small, operation-shaped ports** only when a validated need arises:

| Proposed seam | Owner and contract | Evidence / gate |
|---|---|---|
| Account authorization + protected credential resolution | Commerce application asks provider adapter to begin/complete seller authorization, inspect granted scopes, refresh and revoke through opaque credential reference. | ML seller OAuth [ML-AUTH](https://developers.mercadolivre.com.br/autenticacao-e-autorizacao); TikTok seller flow and Shopee signing details pending. Do not put tokens in `MarketplaceAccount`. |
| Listings read and observation | Fetch seller item IDs/details/pages and normalize into `MarketplaceListing`/`MarketplaceListingObservation`, retaining provider IDs and timestamps. | ML seller search/item detail [ML-ITEMS](https://developers.mercadolivre.com.br/itens-e-buscas). TikTok/Shopee BR listing read remains gated. |
| Publication and inventory commands | Distinct create/edit/status, price and stock operations with a VERCE command ID, desired-state version, read-after-write and explicit provider-specific validation. Provider capability `SUPPORTED`, account grant `GRANTED` and account active are all required before a port is offered as effective. Runtime outage, invalid token, 429 or malformed provider response is reported separately. No S8B seed value is changed by this discovery.

## Normalization and payload policy

Normalize identifiers, known common status class, amounts/currency, time, quantities, SKU/variant links, shipment/tracking class and fee component category. Preserve the original provider code and API version as an **opaque diagnostic value** in a bounded, non-PII provenance field where a future schema permits; do not force unfamiliar statuses into a false canonical state. ML pack and user-product IDs, TikTok package IDs and invoice status remain typed provider-specific related identities, not replacements for the listing/order IDs [ML-PACKS](https://developers.mercadolivre.com.br/pt_br/gestao-packs), [TT-SPLIT](https://partner.tiktokshop.com/docv2/page/split-orders).

Persist normalized observations and Sale facts under their owners. Do not create raw-payload tables. Transient HTTP response bodies can be processed in memory; diagnostic logs should contain only sanitized provider error code, request ID, resource ID and retry context, with tokens and buyer PII redacted. S8B listing observations keep their 180-day retention; Sales/finance retention must be decided under applicable Sales/legal requirements and provider terms, independently [TT-BR](https://partner.tiktokshop.com/docv2/page/br-market-updated-api-workflow-to-support-order-invoice-and-warehouse).

## Marketplace order to canonical Sale

An ingestion candidate needs authorized account identity, provider order ID, creation/update timestamps, currency, status/payment status, lines with provider item/variant/SKU/order-line keys, quantity, gross and charged price, seller/platform discount split, fee source/amount, shipping charge and cost components, and cancellation/refund references. It must map line products through verified `Product`/listing relationships; unresolved mapping should be an explicit reconciliation state, never a silent new Product. `SalesChannel` is derived from the account/channel relationship, not from free text. `Sale` remains the financial source of truth after idempotent ingestion; a provider analytics GMV metric is not added to it.

Use `(MarketplaceAccountId, ExternalOrderId)` as the primary import idempotency identity because ML and TikTok expose distinct order IDs per authorized seller [ML-ORDERS](https://developers.mercadolivre.com.br/pt_br/gerenciamento-de-vendas), [TT-BR](https://partner.tiktokshop.com/docv2/page/br-market-updated-api-workflow-to-support-order-invoice-and-warehouse). Store pack/package/shipment/payment identifiers as related facts; one pack can hold multiple ML orders, and one TikTok order can split packages [ML-PACKS](https://developers.mercadolivre.com.br/pt_br/gestao-packs), [TT-SPLIT](https://partner.tiktokshop.com/docv2/page/split-orders). Shopee ID uniqueness and order/escrow relationship remain unverified. Reimport is an update/reconciliation of the same canonical order, not a second Sale. Stable line identity and multi-event refund identity need endpoint-specific proof in the implementation gate.

ML order `sale_fee` is a provider-reported fact but may be finalized on payment accreditation; discounts have seller/platform components and their own endpoint [ML-ORDERS](https://developers.mercadolivre.com.br/pt_br/gerenciamento-de-vendas). TikTok finance transactions contain realized SKU-level fees, refunds, tax and shipping after order creation, with `seller.finance.info` [TT-FINANCE](https://partner.tiktokshop.com/docv2/page/get-transactions-by-order). Thus `fee_source = PROVIDER_REPORTED` should be assigned only for a captured, reconciled realized fee with the correct lifecycle; absence is not zero and local estimate must not masquerade as actual. Shopee realized-fee availability is UNKNOWN.

The future `COMPLETE` Sales coverage gate still requires effective `ORDERS_READ`, successful sync and full interval/source coverage. ML's 12-month retention and seller search's canceled-order filtering are documented blockers to an unconditional historical claim [ML-ORDERS](https://developers.mercadolivre.com.br/pt_br/gerenciamento-de-vendas). TikTok history/cancellation/refund bounds and Shopee order API remain UNKNOWN. The connector should record intervals and gaps explicitly, not promote a partial scan.

## Publication and ChannelOffer relationship

`Product` provides technical content; `ChannelOffer` holds VERCE's chosen commercial intent; `MarketplaceAccount` selects the authorized seller; `MarketplaceListing` records external identity/state. A publication command snapshots intent and provider-specific category/attribute/variant material at dispatch, validates eligible capability and seller grant, sends the provider operation and later observes the result. External moderation, repricing or stock updates change observed listing state only; they do not silently rewrite the offer. ML supports item create/update/status with category-specific validation and evolving User Products stock routes [ML-PUBLISH](https://developers.mercadolivre.com.br/pt_br/publicacao-de-produtos), [ML-USERPRODUCT](https://developers.mercadolivre.com.br/pt_br/preco-variacao). TikTok BR local listing command semantics and Shopee publication remain unverified.

Minimum command vocabulary for a **later** design: create, edit content/attributes, pause/activate where the provider supports it, change price, set available stock. Each command requires provider-specific validation, externally returned identity, a local idempotency key and a read-back state. Never blindly replay an ambiguous POST. Closing/deleting, catalog matching, moderation and warehouse allocation remain provider-specific; an interface should not promise them universally.

## Sequenced implementation waves and gates

1. **S8C.1 — authorization and connector foundation:** review credential-reference storage, seller grant lifecycle, signed requests, per-provider/account rate budget and sanitized diagnostics. Mercado Livre first because MLB auth and endpoints are publicly documented. TikTok Shop seller auth details must be obtained before its adapter; Shopee requires official BR docs before any implementation.
2. **S8C.2 — listing observation:** implement ML item read/paged sync and safe normalized observations. Add TikTok/Shopee only after BR-local endpoint/scope proof. No write path is needed to validate observation.
3. **S8C.3 — orders and Sales ingestion:** begin ML and TikTok BR order read with explicit interval/gap ledger and idempotent Sale seam; separately verify cancellations, refunds, order-line identity and actual fee timing. No `COMPLETE` claim until measured.
4. **S8C.4 — fee quotes and shipping facts:** ML listing-price quote via existing `IChannelFeeProvider`, with provenance and expiry/context; realized shipping/fees kept separate. TikTok finance transactions inform Sale, not `FEES_QUOTE`. Shopee remains local-rule-only pending a pre-sale fee API.
5. **S8C.5 — publication and stock:** ML first after read reconciliation and command idempotency; account-specific User Products/warehouse and moderation paths need tests. Other providers after official BR write and stock evidence.
6. **S8C.6 — analytics and ads:** ML visits/Product Ads after separate advertiser grant; TikTok Shop analytics and ads only after BR local scope/platform linkage proof. These remain reconciliation/insight data, not canonical Sales totals.

This is an engineering sequence based on documentation completeness, explicit Brazil applicability, testability and dependency order, not a business ranking. TikTok's BR Development Shop is a useful test facility [TT-DEV](https://partner.tiktokshop.com/docv2/page/ar5ppjvv); that does not fill its seller-auth, fee-quote or analytics/ads gaps. Shopee's place is contingent on access to current official BR documents. A later implementation proposal may reorder waves after those gates.

## ADR disposition

No new ADR is warranted now. The provider package boundary, credential mechanism and sync checkpoint model are proposals with open official evidence, while ADR-0023 already freezes the necessary Commerce/Sales ownership. An implementation ADR can be proposed only when an actual cross-module choice is ready to freeze and its provider gates are satisfied.
